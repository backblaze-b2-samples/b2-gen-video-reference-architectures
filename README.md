# B2 reference architectures for generative video

How generative video teams use Backblaze B2 across training-corpus curation, video diffusion training, self-hosted generation farms, hosted multi-provider generation with provenance, moderation and approval, and finishing and delivery. Each architecture documents the data flow, B2 zones and security boundaries, and links out to the third-party integrations and B2 sample applications that implement it.

Learn more about [Backblaze B2 for AI and machine learning](https://www.backblaze.com/cloud-storage/industries/ai-ml).

Start with the [architecture index](docs/architecture-index.md) or the [agent-readable summary](docs/gen-video.md). Current B2 product behavior is documented at [backblaze.com/docs](https://www.backblaze.com/docs/cloud-storage).

## Where does Backblaze B2 fit for generative video?

Generative video produces more data per request than almost any other AI workload. Corpora run from hundreds of TB to PB, checkpoints are large, and each generation leaves behind keyframes, takes, variants and renditions. Hosted model providers return result URLs that expire.

- **Store in B2:** raw footage, curated clips and captions, versioned training shards, checkpoints and LoRAs, model weights, generated outputs, provenance manifests, delivery renditions.
- **Connect to B2:** through a tool's configurable S3 endpoint (`https://s3.<region>.backblazeb2.com`), an explicit Backblaze option, or a presigned-URL handoff for APIs that only ingest URLs.
- **Protect in B2:** Object Lock on dedicated buckets for raw footage, manifests and released weights; legal hold on disputed assets; Cloud Replication for DR only.
- **Automate with B2:** Event Notifications to trigger moderation and verification.
- **Deliver from B2:** CDN partners with no B2 download fees for that egress, and presigned URLs for review and managed-video ingest.
- **Keep elsewhere:** job queues, tracking, rights, MAM and billing databases, in-RAM vector indexes, node-local NVMe caches, GPU VRAM, signing and provider keys, CDN edge caches.

Pricing, egress terms and limits change. See [B2 pricing](https://www.backblaze.com/cloud-storage/pricing) and the [B2 docs](https://www.backblaze.com/docs/cloud-storage).

## B2 capability map

| Area | Capabilities | Selection notes |
|---|---|---|
| Access | S3 API, presigned URLs, CORS, multipart, scoped keys (one bucket + one optional prefix + capabilities) | Default to the S3 API; presigned GET for provider and Mux handoff; native API only for notification rules |
| Change and lifecycle | Event Notifications, versions, lifecycle (hide, then delete, by prefix and age) | Notifications are enabled through Support, at-least-once and signed; lifecycle cannot keep the last K checkpoints |
| Protection | SSE-B2, Object Lock, legal hold, replication | Use governance-mode default retention on raw-footage and manifest buckets; apply retention per released weight version in the models bucket, leaving cached weights without retention; replication is bucket-to-bucket DR |
| Delivery | Server-side copy, bucket-info Cache-Control, CDN partners, compute partners | Private bucket behind a signing edge app by default |
| Performance | Standard B2, [Overdrive](https://www.backblaze.com/cloud-storage/b2-overdrive), local NVMe cache | Standard by default; Overdrive only for measured, sustained training or curation read throughput; NVMe caches for shards and weights |
